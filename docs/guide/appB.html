부록 B. 확인 문제 풀이

0장

  1. 이미지를 받아서 실행한다. 서버에는 소스 코드도 JDK·Node.js 도 없다. Docker Hub 에서 docker compose pull 로 받은 이미지를 켤 뿐이다.
  2. 80번 하나. frontend 컨테이너의 nginx 가 받아서 화면은 직접 주고, /api 는 게이트웨이로 넘긴다.
  3. 무료 EC2(t3.micro)는 메모리가 1GB 다. 서비스 3개 + DB 만으로도 거의 꽉 차서 Kafka 까지 올릴 자리가 없다.

1장

  1. React 코드는 사용자의 브라우저에서 돈다. 그 안의 localhost 는 사용자 자신의 PC 이고, 그곳에는 게이트웨이(8080)가 없다.
  2. nginx 는 /posts/3 이라는 파일을 찾지 못해 404 를 돌려준다. index.html 을 줘야 React Router 가 주소를 보고 3번 글 화면을 그린다.
  3. 환경 변수 JWT_SECRET 이 없을 때만 쓰인다. 내 PC 에서 그냥 실행할 때가 그렇다. 서버에서는 .env 의 값이 들어가므로 쓰이지 않는다.
  4. ① npm run dev 는 소스를 그때그때 변환하는 개발용 서버라 느리고, 서버에 Node.js·소스 코드가 있어야 한다. Nginx 는 npm run build 로 만든 완성 파일만 빠르게 내려준다. ② Nginx 를 앞에 두면 화면과 API 가 주소 하나(80) 에서 나와 CORS 가 필요 없고, 게이트웨이·서비스·DB 포트를 바깥에 열지 않아도 된다. (새로 고침 404 를 막는 try_files, 나중의 HTTPS 도 Nginx 에서 처리한다)
  5. Nginx 는 주소 앞부분만 본다 (/api/ 로 시작하면 게이트웨이로, 아니면 React 파일). 우리 앱의 업무는 모른다. API Gateway 는 토큰과 경로를 본다 (토큰이 맞는지 검사하고, /api/auth 는 user-service, /api/posts 는 post-service 로). Nginx 는 바깥 문, 게이트웨이는 안쪽 문이다.

2장

  1. 실행에는 컴파일러가 필요 없기 때문이다. JRE 만 넣으면 이미지가 작아지고, 서버에서 받는 시간과 디스크가 줄어든다. 컴파일러·소스가 없으니 보안에도 낫다.
  2. Docker 는 단계마다 결과를 캐시한다. build.gradle 이 그대로면 "라이브러리 받기" 단계를 캐시에서 꺼내 쓰므로 소스만 고친 빌드가 훨씬 빨라진다.
  3. 컨테이너 안에서 localhost 는 그 컨테이너 자신이다. DB 는 다른 컨테이너이므로 compose 가 만들어 준 이름 db 로 찾고, 포트도 컨테이너 안쪽 포트(5432)를 쓴다. 5435 는 MSA 기초 과정에서 내 PC 에 열어 둔 바깥 포트였다.
  4. 고장이 아니다. 8080 은 일부러 바깥에 열지 않았다(ports 없음). 모든 요청은 80(nginx)을 거쳐 들어가야 한다.

3장

  1. 사용자 이름 rlaeocjf, 저장소 이름 msa-frontend, 태그 latest.
  2. 토큰 권한이 Read-only 다. Read & Write 토큰을 새로 만들어 docker login (또는 DOCKERHUB_TOKEN Secret)을 다시 한다.
  3. 공개 이미지는 누구나 받아서 안을 열어 볼 수 있다. 비밀번호가 이미지 층(layer)이나 환경 변수에 남아 있으면 그대로 드러난다.

4장

  1. 리전마다 화면과 자원이 따로라서, 다른 리전에 만들면 서울 화면에서는 보이지 않는다. 사용자와 먼 리전은 느리기도 하다.
  2. 그 인스턴스에 다시 SSH 로 들어갈 수 없다. AWS 도 개인 키를 갖고 있지 않아 다시 내려받을 수 없다. 새 키 페어로 인스턴스를 새로 만들어야 한다.
  3. 바깥에서 들어오는 문은 80(nginx)뿐이고, nginx → 게이트웨이 → 서비스 → DB 는 EC2 안의 도커 네트워크로 오간다. 보안 그룹은 EC2 바깥의 문만 지킨다.

5장

  1. 5-1 의 icacls 로 상속 권한을 지우고(/inheritance:r) 나에게만 읽기 권한을 준다.
  2. 사용자가 속한 그룹은 로그인할 때 정해진다. 이미 열린 접속에는 새 그룹(docker)이 반영되지 않는다.
  3. 아니다. Spring 서비스가 아직 켜지는 중이다. 30초~1분 기다렸다가 새로 고침한다. 계속 502 면 docker compose ps, logs 를 본다.
  4. .env 를 빠뜨렸을 때 약한 기본 비밀번호로 조용히 켜지는 사고를 막기 위해서다. 값이 없으면 바로 오류를 내고 멈춘다.

6장

  1. Variables 는 로그에 그대로 보이고, Secrets 는 암호화되어 로그에 *** 로 가려지며 다시 볼 수도 없다. EC2_HOST 는 브라우저로 누구나 접속하는 공개 주소라 숨길 까닭이 없고, 로그에서 어디로 배포했는지 보이는 편이 오류를 찾기 쉽다.
  2. deploy 잡은 needs: build 라서 시작하지 않는다(건너뜀). 서버는 예전 버전 그대로 돈다.
  3. 502: nginx 는 켜졌지만 api-gateway 가 아직 응답하지 않는다. 503: 게이트웨이는 켜졌지만 뒤의 post-service 가 아직 준비되지 않았다.
  4. PostgreSQL 은 처음 만든 비밀번호를 그대로 쓰므로, 서비스가 새 비밀번호로 접속하다 password authentication failed 로 실패한다. 배포 확인 스텝이 3분 뒤 실패한다.

7장

  1. 9시간 이른 오전 6시로 저장된다. (UTC = KST - 9시간)
  2. 시간대 설정은 앞으로 저장할 시각에만 영향을 준다. 이미 DB 에 저장된 값은 그대로다.
  3. GitHub Variables 의 EC2_HOST 를 새 퍼블릭 IP 로 바꾸고 Run workflow 로 다시 돌린다.
  4. 중지는 껐다 켤 수 있고 디스크(데이터)가 남는다(IP 는 바뀐다). 종료는 인스턴스를 버리는 것이라 디스크까지 지워지고 되돌릴 수 없다.

8장

  1. 아니다. 컴퓨터 요금은 멈추지만 디스크(EBS 20GiB) 요금은 계속 나간다. 실습이 끝났으면 종료한다.
  2. 인스턴스가 "종료됨" 상태가 될 때까지 기다린다. 몇 분 뒤 다시 지운다.
  3. Variables 의 EC2_HOST 를 지운다. deploy 잡이 if: 조건으로 건너뛰어진다.
  4. 어느 코드로 만든 이미지인지 알 수 있고, 문제가 생기면 그 태그로 예전 버전을 바로 다시 켤 수 있다.
